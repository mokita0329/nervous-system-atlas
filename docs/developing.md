# Developer guide

For anyone who wants more than `npm start`: hosting a copy, showing an MRI of their own on the slices,
regenerating the data, running the checks, or changing the code. What the app does is in the
[user guide](guide.md); the rules for sending a change back are in [CONTRIBUTING.md](../CONTRIBUTING.md);
the operating manual with the traps that cost time is [AGENTS.md](../AGENTS.md).

## Prerequisites

| | |
|---|---|
| **Node 22+ and npm** | the app, the content build and every `npm run` check. `package-lock.json` is committed — use `npm ci`, not `npm install` (`npm start` does). |
| **[uv](https://docs.astral.sh/uv/)** | the Python pipeline in `pipeline/` is a uv project (`requires-python = ">=3.12,<3.13"`). Only needed to regenerate data or register your own MRI. |
| **Python 3.12+** | the standalone tools under `tools/` (`tools/i18n/prose.py`, `tools/cite/*.py`). `prose.py` is pure standard library — plain `python3` is enough, no venv. |
| **Playwright chromium** | `npx playwright install chromium`, for the browser tests (`npm run e2e`). |
| **Blender `bpy`** | only if you touch the Z-Anatomy export (`blender/`). |

## The three commands

```bash
npm start                  # npm ci if needed → fetch the data bundle once → vite at http://localhost:5173
npm run check              # the whole check suite, in the release order; --quick skips the build and the browser tests
npm run data:build         # regenerate public/data/ from the source atlases instead of downloading it
```

Underneath them: `npm run dev` serves without fetching, `npm run data` fetches without serving, `npm run build`
writes `dist/` and gates it, `npm run preview` serves `dist/`. Every other script is listed in `package.json`
and named under [Checks](#checks) below.

## Where things are

| Path | What |
|---|---|
| `src/` | the app: Vite + TypeScript + three.js, plain DOM, no framework. `scene/` renders, `state/` is the store and the actions, `ui/` the panels, `router/` the hash router, `i18n/` the interface strings. |
| `content/` | the authored entries as JSON, one file per entry under `data/<kind>/`, the zod schemas in `schema/`, the bibliography, and the Turkish overlays under `i18n/tr/`. |
| `pipeline/` | the Python pipeline that builds the meshes, volumes, label tables and manifest; `config/sources.yaml` is the licence and download record every guard reads. |
| `scripts/` | the Node side: `start.ts`, `check.sh`, `build-data.sh`, the content build (`content/`), `fetch-data.ts`, the gates (`check-public.ts`, `check-tree.ts`, `check-data.ts`), `notice.ts`, `release-data.sh`. |
| `tools/` | standalone Python: `author/` (entry helpers), `cite/` (bibliography tooling), `i18n/` (terminology table and prose overlays). |
| `tests/`, `e2e/` | vitest unit tests and Playwright browser tests. |
| `public/data/` | the generated data — **gitignored, never committed**; either fetched by `npm run data` or written by the pipeline. |
| `docs/` | this documentation, the screenshots and the icon. |

## How the data gets there

Meshes, MRI volumes, label tables and `manifest.json` are generated by the pipeline from downloaded source
atlases. They are large and fully regenerable, so they are not in the repository: a fresh clone has no
`public/data/`, and the app boots to a message saying what to run. Two ways to fill it:

- **Download the released bundle.** `npm run data` (which `npm start` does for you) fetches the release asset of
  the current version — 49 MB, verified against the SHA-256 pinned in `scripts/fetch-data.ts`. This is what
  almost everyone wants.
- **Build it.** `npm run data:build` runs the pipeline end to end; see [Building the data yourself](#building-the-data-yourself).

Without the data, straight after `npm ci`, these still work: `npm run typecheck`, `npm run content:validate`,
`npm run citations:check`, `npm run notice -- --check`, `npm run build`, the unit tests that do not read the
data (the others skip themselves) and `python3 tools/i18n/prose.py check`. That is the set CI's `node` job
runs; its `integration` job then fetches the released bundle and runs the browser tests on it.

## Hosting a copy

```bash
npm run build              # atlas-manifest → content → vite → filter dist/data → check-public
```

`dist/` is a static site: copy it to any web server or object store, no runtime needed. The build ends in
`scripts/check-public.ts`, which refuses to leave a `dist/` that contains anything the public edition may not
ship — so what `npm run build` produces is redistributable by construction. `.github/workflows/pages.yml`
deploys exactly this to GitHub Pages, fetching the same release asset rather than anything in the repository.
Never publish `dist-private/` (see [The two editions](#the-two-editions)).

## Showing your own MRI

The atlas is a template, and everything in it — meshes, label volumes, slices — lives on one MNI152NLin2009cAsym
grid. A personal scan is therefore not something the atlas adapts *to*; it is carried *into* that frame, where the
structures already line up, and appears in the contrast menu next to T1 and T2:

```bash
cd pipeline && uv sync --extra subject && cd ..                     # antspyx for the registration, dcm2niix for DICOM
uv run --project pipeline atlas-subject path/to/patient-cd.zip --id me
```

Give it what you have: the zip or folder a hospital hands out (DICOM — every series is converted with
[dcm2niix](https://github.com/rordenlab/dcm2niix), the one that looks like a whole-head 3D T1 is taken, the
table is printed, `--series N` overrides), or a NIfTI. It then does N4 bias correction, rigid + affine + **SyN**
registration onto the atlas's own MNI T1w — the full `antsRegistrationSyN` recipe, five to ten minutes (affine
alone leaves the gyri millimetres off the parcels; the deformable stage is what puts the cortical labels on
*your* sulci), a resample onto the atlas grid, and **defacing** with a plane derived from the template's brain
mask that cannot cut brain. Look at `pipeline/qa/subjects/me/` — especially `skin-front.png`, the skin surface
seen from the front — before you share anything. The volume needs a `subject_me` entry in
`pipeline/config/sources.yaml` (its licence and a line saying whose scan it is), and the three guards refuse a
subject volume that is undefaced, unattributed or not redistributable. The scan itself never enters the
repository. A shared link carries the choice: `#/slice?c=subject-me&ax=-2`.

## Building the data yourself

The bundle that `npm start` fetches is generated; `npm run data:build` regenerates it from the source atlases:

```bash
npm run data:build         # uv sync → atlas-build (download → volumes → register → meshes → labels → manifest → QA) → check-data → content
npm start
```

This downloads several GB and takes a long time; you only need it to change how the meshes or volumes are
made. The individual steps, the optional extras (Z-Anatomy, the public-edition cord MRI, the manually
downloaded Brainstem Navigator toolkit) and the registration and meshing notes are in
[Building the data](pipeline.md).

## The two editions

The atlas is built twice from the same tree.

The **public edition** is what may be redistributed — Apache-2.0 code, CC BY-SA 4.0 data and content — and it
is the default everywhere: `npm run dev` serves it, `npm run build` builds it into `dist/`, and
`scripts/check-public.ts` gates that build before you can publish it. The **private edition** additionally
contains four datasets whose licence is non-commercial or forbids passing derived files on, so it never leaves
the machine that built it: `npm run dev:private`, `npm run build:private`.

| Dataset | Licence | Why it cannot ship | Replaced in the public edition by |
|---|---|---|---|
| Harvard-Oxford (FSL) | `FSL-NC` | held back pending review — FSL relicensed it to CC BY-SA 4.0 in Aug 2025 | CerebrA/DKT cortical parcels (CC0) |
| Diedrichsen cerebellar atlas | `CC-BY-ND` | no derivatives may be distributed | a FastSurfer CerebNet segmentation of our own template (CC BY-SA 4.0) |
| Brainstem Navigator 7 T nuclei | `BrainstemNavigator-NC-ND` | derived files may not leave the organisation | the Dahl locus coeruleus meta-mask (CC BY 4.0) and landmark-anchored markers built from published volumes |
| PAM50 cord template | `PAM50-unlicensed` | the repository ships no licence at all | a cord MRI composed here from spine-generic and Fudan whole-spine data (CC BY 4.0) |

Nothing is special-cased by name: a dataset leaves the public edition when its licence record carries
`nc: true` or `no_redistribution: true`. Those four sit in the `restricted` download group, which
`atlas-download` fetches only on the `private` branch or with `ATLAS_ALLOW_RESTRICTED=1`, so a plain clone of
`main` cannot build data it may not share. In `public/data/` the plain names (`manifest.json`, `content.json`,
`search-index.json`, `content.tr.json`) are always the public edition; the private one, where it exists, is
`manifest.private.json` and friends. The reasoning behind each substitution, and how to obtain the restricted
datasets if you are entitled to them, is in [The two editions](editions.md).

## Checks

`npm run check` runs the whole suite in the order the release checklist uses, skips what the machine cannot
run (no `public/data/`, no `uv`, no Playwright chromium) and says so in the summary; `--quick` leaves out the
build and the browser tests and takes about a minute. One step at a time:

```bash
npm run check-tree                                # no restricted, private or generated file is committed
npm run typecheck
npm test                                          # vitest; the tests that need data skip without it
npm run content:validate                          # schemas, cross-links, word minimums, spelling, coverage
npm run citations:check                           # citation form, unverified or uncited entries, and the counts the docs quote (--fix rewrites them)
node scripts/check-data.ts                        # integrity of public/data/ (--all: both manifests)
npm run notice -- --check                         # NOTICE is generated; never edit it by hand
uv run --project pipeline atlas-qa                # the pipeline's own data gates; needs pipeline/work/
npx playwright install chromium && npm run e2e    # browser tests against the dev server
npm run build                                     # builds dist/ and runs the redistribution gate over it
python3 tools/i18n/prose.py check                 # Turkish overlays against the English entries
```

**What CI runs.** `.github/workflows/checks.yml` has a `node` job with everything that works without generated
data, an `integration` job that fetches the *last released* bundle, rebuilds the content bundles from the commit
(`npm run content`) and runs the browser suite on that, split over two runners with one browser each, and a
translations job. The runner has no GPU, so every
timeout in the specs is multiplied by `SLOW` (4 when `CI` is set) — write new waits as `{ timeout: N * SLOW }` —
and a browser test may only read pipeline output the released bundle ships. The build gate over data that is not
yet released, `check-data` and `atlas-qa` are yours to run locally.

## Content, citations and translations

The entries are JSON under `content/data/`, validated by the schemas in `content/schema/`, and every
non-glossary entry cites open-access sources only. [Content and citations](content.md) has the schemas, the
authoring helpers and the citation tooling; [The Turkish edition](turkish-edition.md) has the terminology
table, the overlay format and `tools/i18n/prose.py`. The rules a change must meet are in
[CONTRIBUTING.md](../CONTRIBUTING.md#adding-or-editing-content).

## Releasing

The data ships as a release asset, never in the repository, and a new version means a new asset name. The
sequence — `npm version`, `scripts/release-data.sh`, the GitHub release, the asset upload *before* the pin is
pushed — is in [AGENTS.md](../AGENTS.md#releasing).
